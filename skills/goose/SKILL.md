# Goose Skill

Handles Goose migration operations with correct CLI commands — proper timestamps generated by the tool, not fabricated.

## When to Use

- Creating new database migrations in Go projects
- Applying or rolling back migrations
- Checking migration status
- Fixing migration sequence issues

## Default (No Arguments)

If invoked without arguments, use `AskUserQuestion` to present available operations:

| Operation | Description                                    |
| --------- | ---------------------------------------------- |
| `create`  | Create new migration file with real timestamp  |
| `up`      | Apply all pending migrations                   |
| `down`    | Roll back the last migration                   |
| `status`  | Show migration status                          |
| `fix`     | Re-order migrations by timestamp               |
| `redo`    | Roll back last migration, then re-apply it     |

## Arguments

### `create` — Create New Migration

**CRITICAL: Always use `goose create` to generate migration files. NEVER fabricate timestamps or create migration files manually.**

```bash
# Always create SQL migrations
goose -dir <migrations-dir> create <descriptive_snake_name> sql
```

Goose generates the correct timestamp prefix automatically: `20260407120305_descriptive_snake_name.sql`

#### Migration Naming Convention

Use descriptive snake_case names (goose convention):

- `add_user_email_column`
- `create_orders_table`
- `add_draft_status_to_posts`
- `add_index_on_created_at`

**BAD examples (never do this):**
- Manually creating `20260407000000_add_column.sql` — fabricated timestamp
- `migration.sql` — too generic
- `fix.sql` — not descriptive

### `up` — Apply Migrations

```bash
# Apply all pending migrations
goose -dir <migrations-dir> postgres "<dsn>" up

# Apply one migration
goose -dir <migrations-dir> postgres "<dsn>" up-by-one

# Apply up to a specific version
goose -dir <migrations-dir> postgres "<dsn>" up-to <version>
```

### `down` — Roll Back

```bash
# Roll back last migration
goose -dir <migrations-dir> postgres "<dsn>" down

# Roll back to a specific version
goose -dir <migrations-dir> postgres "<dsn>" down-to <version>
```

**DESTRUCTIVE: Always confirm with user before rolling back.**

### `status` — Migration Status

```bash
goose -dir <migrations-dir> postgres "<dsn>" status
```

### `fix` — Fix Migration Sequence

Re-orders migrations by timestamp when sequence numbers conflict.

```bash
goose -dir <migrations-dir> fix
```

### `redo` — Redo Last Migration

Roll back and re-apply the last migration. Useful during development.

```bash
goose -dir <migrations-dir> postgres "<dsn>" redo
```

## DSN Formats

```bash
# PostgreSQL
goose postgres "host=localhost port=5432 user=app dbname=mydb sslmode=disable" up

# From environment variable
goose postgres "$DATABASE_URL" up

# MySQL
goose mysql "user:password@tcp(localhost:3306)/mydb" up

# SQLite
goose sqlite3 ./mydb.sqlite3 up
```

**IMPORTANT:** Never hardcode credentials in commands. Use environment variables or `.env` files.

## SQL Migration Template

Goose uses `-- +goose Up` and `-- +goose Down` annotations:

```sql
-- +goose Up
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    status TEXT NOT NULL DEFAULT 'pending',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- +goose Down
DROP TABLE IF EXISTS orders;
```

## Important Rules

1. **NEVER fabricate migration files or timestamps** — Always use `goose create` which generates correct timestamps
2. **NEVER skip writing the `-- +goose Down` section** — Always include rollback SQL
3. **Always check `goose status`** before deploying
4. **Confirm destructive operations** (`down`, `redo`, `reset`) with user
5. **Use environment variables** for database credentials, never hardcode
6. **Detect migrations directory** — Check for common paths: `migrations/`, `db/migrations/`, `sql/migrations/`, or project-specific config
7. **Use `-- +goose StatementBegin/End`** for multi-statement migrations:
   ```sql
   -- +goose Up
   -- +goose StatementBegin
   CREATE OR REPLACE FUNCTION update_timestamp()
   RETURNS TRIGGER AS $$
   BEGIN
       NEW.updated_at = NOW();
       RETURN NEW;
   END;
   $$ LANGUAGE plpgsql;
   -- +goose StatementEnd
   ```

## Schema Drift

When DB schema diverges from migration history:

1. Run `goose status` — identify applied vs pending
2. If DB was modified outside goose:
   - Create a new migration that captures the current state: `goose create baseline sql`
   - Write the diff SQL in the Up section
   - Mark as applied if DB already has the changes (insert into `goose_db_version` table)
3. If migrations were applied out of order: `goose fix` to re-sequence
